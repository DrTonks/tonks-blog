# 自动图片优化：管理流程与实测结果

## 当前已实施（2026-09-08）

原图仍放 public/images/albums、projects、covers；JSON/文章/贴纸继续写原始路径。Astro 集成在 dev/check/build 启动时扫描素材，生成内容指纹缓存，生产构建只将本轮使用的派生图复制至 dist/_images。缓存位于 node_modules/.cache/blog-images，不提交；删除源图后，旧缓存不会再次部署。没有修改源图片、项目 JSON、时间线 JSON 或相册扫描器。

- 相册封面/列表照片、项目卡片、贴纸候选池、文章列表/站内引用卡片：最长边800px的缩略版本，不放大。
- 相册 Fancybox 大图、时光机、文章正文封面/public banner：保留原分辨率的展示版本（不是缩小到2048）。
- 照片/封面 WebP quality85，项目截图 quality90；派生文件若不比原图小就使用原图。保留透明度、校正方向；派生图不携带原EXIF，原文件仍保持原状。
- JSON-LD等原始资源元数据及其他未接入入口仍可使用原图，这是兼容路径，不是漏删文件。
- CDN 已上传的11张图片继续使用此前验证的WebP映射，未更改OSS。

管理方式：加相册、放照片、维护 cover.jpg/info.json；加项目图片后改 projects.json；时光机和贴纸配置照旧。正常构建自动纳入新图，无手动改后缀或维护第二套清单。当前项目/时光机 JSON 及文章封面中的 /images/ 文件缺失会中断构建并报出路径；动态外链不会被当作本地文件检查。

新增后不构建而只更新线上JSON/原图，旧清单找不到新条目时仍回退原URL；下次构建才获得优化版本。dev运行期间新增/替换素材，需要重启dev进程以刷新优化清单；不会在每次鼠标交互或每次请求时实时压缩。源图替换生成新指纹，但不能在不构建的情况下承诺旧派生URL自动变更。

## 体积结果

| 素材集合 | 原始文件合计 | 缩略版本合计 | 原分辨率展示版本合计 |
| --- | ---: | ---: | ---: |
| 相册72张（含7张封面） | 21,040,943 B | 5,001,398 B（-76.2%） | 12,918,554 B（-38.6%） |
| 项目24张 | 6,778,601 B | 951,064 B（-86.0%） | 1,393,236 B（-79.4%） |
| 封面7张 | 598,140 B | 56,140 B（-90.6%） | 56,140 B（-90.6%） |

当前9个项目引用的9张不同封面合计从1,623,697 B降至279,784 B，减少82.8%。这些是资源大小汇总，不是单页加载时间/LCP实测；懒加载、缓存、重复引用会改变真实请求总量。相册大图依旧有按需请求及现有Fancybox预加载成本。

原图保留的代价：dist/_images共166个文件（含公开manifest），增加17,558,922 B，约16.75 MiB。小图两种规格相同会复用文件。磁盘缓存可以大于部署派生目录，因为保留旧编码缓存；清除node_modules/.cache/blog-images只影响下一次编码时间。

浏览器URL查找表原始JSON14,329 B，单独gzip3,213 B；这是查找表自身的压缩量，不是整个构建JS差值。查询为直接字典查找，发生在渲染时，没有DOM扫描、MutationObserver、RAF或浏览器转码。初始化内存增加字典和模块对象，未实测进程内存/能耗。

## 构建与验证

首次本机图片生成8,557ms（当时190次编码，后续去除了小图重复规格）；首次整个Astro构建13.71s。缓存命中时生成阶段约52ms、0次编码，完整构建5.14–5.30s；之前无此流水线一次构建5.27s。不是隔离严谨A/B，不声称构建加速；主要新增成本集中在首次及换图编码。

- 44页生产构建通过；Node5项测试通过，覆盖新增、同名覆盖、删除、缓存复用、源内容保留、无效JSON图片引用、CDN回退、主题相关回归。
- 全部103个源URL及206个缩略/展示目标路径存在，项目/时间线JSON构建产物与源文件逐字节相同。
- 真实浏览器验证无锡相册仍13张、缩略/展示URL分离、Fancybox正常显示；项目运行时JSON加载后卡片使用WebP。时光机/贴纸/文章入口通过构建产物与路径检查，不能把这些说成每个页面都做过人工视觉验收。
- Astro check仍52个既有错误；没有宣称全项目类型检查通过。
- 未执行生产部署。发布时上传完整dist（包含_images），不要只上传HTML或旧资源目录。

## Sleepy 协同修改

sleepy已在最新远端b8b290c基础上修改：image与images在返回副本上同步规范化为博客绝对URL，保留项目字符串/时光机数组的形状。源JSON不变。旧 /images/projects/... 302跳转博客、缓存300秒，不再要求sleepy目录里存在图片；其他本地图片和音乐路由保持原行为。旧images文件未删除，可以停止维护。

复用 SLEEPY_BLOG_BASE_URL（默认https://blog.tonks.top）。接口仅请求原来的两个数据JSON，不逐图请求，不代理图片字节。图片URL限定到配置博客域及/images路径，拒绝外域和目录穿越。4项纯函数测试、32项API回归通过；API测试包括本地不存在的新图仍返回正确URL，以及两个字段保持一致。

现在sleepy直连的是博客原图地址，不读取WebP指纹清单，因此它的主要收益是消除重复存储/维护和后端图片传输，而不是主页图片下载量下降。以后若要主页也自动选用优化版本，可以缓存博客/_images/manifest.json并保留原图回退；本轮没有加入额外远程清单请求和启动等待。

建议发布顺序：先发布博客完整dist并检查原图仍200，再发布sleepy并检查/blog-posts中的两个字段及旧图片302。不要删除sleepy旧文件直到实际线上验证和回滚窗口结束。变更尚未提交、推送或部署。
