## 后续 WebP 优化更新（当前实现）

下面 A/B 帧率、初始化与产物表记录的是压缩前的 PNG 候选，保留作历史测量，不能将其 580 KiB 图片增量当成当前值。现已将两张头像构建为 512×512 WebP：27,784 B + 26,862 B = **54,646 B**，相对两张原 PNG 减少 **91.2%**，相对远端原单张 WebP 的净增加为 **27,136 B（26.5 KiB）**。无引用的构建 PNG 副本也被清理，源文件保留。详见 [图片优化](./image-optimization.md)。

本次编码改动不改变粒子网格、shader 或动画调度。两张解码图像的理论 RGBA 像素存储从 3.125 MiB 降为 2 MiB；GPU 纹理仍合计 512 KiB。不据此声称帧率或 GPU 耗时提升；下方初始化数字没有针对 WebP 重新做严格 A/B。

## 2. 初始化与静止状态

基线没有头像 WebGL 初始化。候选初始等待 1200ms，然后在空闲调度中准备图像、路径、shader 和纹理；未就绪点击走静态主题切换，不等 GPU 初始化。

本机最终候选一次观测：

- WebGL `getContext` 调用耗时约 **4.4ms**。
- 编译、链接、状态查询、bufferData 和 texImage2D 等被测调用合计约 **18.7ms**。
- 另一次同类暖启动观测约 2.7ms + 5.0ms，说明编译/驱动缓存影响很大。
- 之前测得固定路径预计算约 1.5–1.8ms；这不是上述调用统计内的部分，也不是本轮完整初始化实测。

这些是 JS 调用墙钟耗时，不是 GPU 完成时间；完整初始化还包括 JS、图片 decode、2D 缩放等，不能将上述相加当成完整总耗时。最终两组启动后 5 秒观察均未记录到 >50ms 的 Long Task，不代表低端设备不会出现初始化尖峰。

静止状态：两组额外 2 秒测试均为 **0 次头像 draw call**；候选 RAF 在过渡结束时停止，但缓存的 WebGL 资源不释放，留待下次切换。

## 3. 实际切换：本机无明显退化，但确有新增工作

最终对比使用同一个真实内置浏览器标签页，同为 **1280×720、DPR 2**。每组 9 次按钮点击，其中 6 次实际亮暗变化，另外 3 次系统/亮色同外观切换单独排除。每次点击后采样固定 1600ms，测量时不截图、不滚动；保留首页原有背景/水波等行为。每条记录包含视口。一个 DPR 1 的调试批次未混入最终对比。

| 指标（6 次实际主题变化） | 远端基线 | 最终候选 |
| --- | ---: | ---: |
| 每次头像 draw calls | 0 | **64** |
| 每次帧间隔 P95 | 17.4–17.5ms | 约 17.6ms |
| 最大帧间隔 | 33.87ms | 34.27ms |
| 每次 >25ms 帧间隔数 | 1–2 | 1–2 |
| >50ms 帧间隔 / Long Tasks | 0 / 0 | 0 / 0 |
| 点击至全页扩散释放 | 约 634–645ms | 约 595–611ms |
| 点击至头像最终恢复静态 | 原图始终静态 | 约 **1195–1212ms** |

扩散名义时长两组均为 560ms；表中多出的是点击、截图准备和帧调度。候选改用共享 WAAPI 时钟，测得释放略早，不应解读为 GPU 更快。候选在全页暂停解除后仍重组约 600ms，与其他恢复的动画同时运行，这是整套方案新增的竞争窗口。主题切换互斥也保持到头像结束，比原来约长 0.55–0.58 秒。

64 次 × 16,384 粒子，约为每次切换 **105 万次顶点处理**，不是 105 万个常驻粒子。纹理采样、混合、Canvas 清除与合成也有成本，即使帧率接近刷新率上限，它们并不免费。

相比前一版预计算但没有浪头的方案，本机同布局从约 53 次绘制变为 64 次；增加发生在浪头实际接触头像之后，之前复用首帧。波浪不增加顶点缓冲，使用现有 UV、共享圆心/半径和简单多项式波形；只有波浪阶段需要计算径向距离，进入重组的前 153ms 内淡出，随后统一分支跳过波浪计算。

## 4. 能与不能得出的结论

降级实测：审计环境令头像 WebGL getContext 返回 null，完成暗→亮、亮→暗各一次及一次同外观切换；上下文创建与粒子绘制均为0，头像始终 static，圆形主题切换正常结束。这是故障注入验证，不是无 GPU 硬件的性能测试。

可以确定：下载增加约 580 KiB、新增一个 WebGL 上下文和上述逻辑资源、切换增加 64 次头像绘制、动画/互斥窗口更长；本机最终样本未观察到明显新增掉帧，静止不持续绘制。

不能确定：GPU 时间或能耗增加百分比、低端手机/集显/软件渲染器是否都流畅、大量其他 JS/WebGL 并行动画时的表现。没有 GPU timer query、能耗计、硬件降速或真实低端设备测试。rAF 间隔反映调度，不保证每次绘制都已由 GPU 按时呈现；Long Task 也不能检测所有掉帧。不能以“约 60 FPS”推出“无负担”。

本地审计服务器只在 `?audit=1` 页面注入相同的轻量采样脚本，测量本身有小量开销；两组不截图运行，但随机横幅/贴纸状态和系统负载没有完全锁定。本报告不是实验室统计显著性测试。网络本地无节流、无 CDN，不能拿 localhost 下载时间评价线上首访。

## 5. 合并建议

**动效本身可保留为候选；不建议以当前未经优化的双 PNG 直接作为最终上线方案。** 优先将两张静态图交给现有 Astro 图片管线或评估高质量 WebP/AVIF，保留 PNG 源文件，再复核清晰度和体积。此轮只报告，没有擅自改图片编码。

若更偏向保守性能：静态双头像仍可保留，而粒子动画做可关闭选项，移动/低性能设备只用原有圆形切换。现有 reduced-motion、WebGL 不可用、未准备好、离屏、页面隐藏/滚动/resize 的降级或取消路径继续保留。`failIfMajorPerformanceCaveat` 不是可靠的硬件档位识别，也不能代替低端实测。
