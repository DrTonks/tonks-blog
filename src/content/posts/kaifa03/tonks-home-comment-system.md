AI审核功能沿用了桌宠的模型调用路径。

> 写作提示：本文只保留章节骨架、对比维度和代码入口。`[补充]` 处由作者填写设计判断、体验与开发故事。

## 一、需求起点：静态博客为什么仍然需要自己的互动层

- 只开放“关于本站”和“友链”两个房间
- 无账号体系，但昵称与邮箱必填
- 支持回复树、点赞、管理员发言与删除
- 评论先经过自动审核，管理员在 tonks-home 集中管理
- [补充] 从普通文章底部评论区改造成“群聊”的原因

## 二、为什么是 About / Friends 两个群聊

- 页面与房间的一一映射
- 左侧房间列表：当前只开放两个，数据结构允许继续扩展
- 中间消息流：回复展示为 `@某人`
- 站长消息靠右，访客消息靠左
- 右侧成员列表：按公开发言聚合，而非真实账号在线状态
- [配图] QQ 式三栏界面与移动端单栏切换

## 三、系统架构

```text
blog.tonks.top
  -> 点赞、发表评论、回复、友链申请

tonks.top / Tonks' Chat
  -> 浏览公开评论
  -> 访客填写身份后发言
  -> 管理员审核、删除、查看友链申请

Sleepy / Flask + SQLite
  -> 评论树、点赞、身份哈希、限流
  -> AI 审核
  -> 头像解析
```

- 前端：Astro + TypeScript；Vue 3 + TypeScript
- 后端：Flask + SQLite
- 数据边界：邮箱只在后端保存，不在公开评论接口返回

## 四、数据模型：评论不是扁平列表

### 4.1 评论树

- `parent_id`：直接回复对象
- `root_id`：所属根评论
- 删除父评论时对子树的处理
- 页面维度：`about` / `friends`

### 4.2 审核状态

- `published`
- `pending`
- `rejected`
- `deleted`
- 公开接口与管理员接口返回字段的差异

### 4.3 访客身份

- 昵称、邮箱、可选网站
- 邮箱标准化后生成内部 `actor_hash`
- 对外使用再次派生的 `author_key`
- 浏览器 `X-Client-ID` + IP 哈希 + 邮箱哈希的组合限流

## 五、头像：邮箱既是联系信息，也是可选头像来源

- QQ / Foxmail 数字邮箱：`q1.qlogo.cn/g` 接口
- 其他邮箱：MD5 派生 Gravatar URL
- 无头像或加载失败：后端生成的确定性 SVG / 站点默认头像
- Tonks' Chat 左上角：未填写身份时显示本站头像，填写后预览访客头像
- 隐私边界：公开数据不返回原始邮箱

## 六、评论提交与回复流程

### 6.1 博客端

- 默认折叠输入区，点击“参与留言”后展开
- 根留言与动态生成的行内回复表单共用 API
- Unicode 表情选择器：只插入文本，不增加媒体存储面
- [补充] 四套主题下的样式适配

### 6.2 tonks-home 端

- 首次发送时弹出访客身份表单
- 身份可选择保存在本地
- Enter 发送，Shift + Enter 换行
- `?open=community` 深链：自动展开主页组件并打开群聊

### 6.3 为什么暂不支持图片消息

- 对象存储与访问权限
- MIME、扩展名、尺寸与内容校验
- 图片审核与恶意文件风险
- 配额、生命周期、删除评论后的垃圾回收
- CDN、防盗链与成本
- [补充] 未来开放图片前必须满足的条件

## 七、点赞系统

- 页面点赞：关于本站、友链
- 文章点赞：文章列表与文章页
- 匿名访客去重策略
- 点赞总数与当前访客状态的批量查询
- 物理心形动画只属于表现层，不参与计数逻辑
- [补充] 动画从简单粒子到碰撞/堆积效果的迭代

## 八、AI 审核：复用调用通道，不复用桌宠人格

### 8.1 复用的部分

- `PetAIConfig`
- `OpenAICompatibleProvider`
- 同一组模型 endpoint / key / timeout 配置

### 8.2 明确隔离的部分

- 独立的 `CommentModerationService`
- 独立提示词 `comment_moderation_prompt.md`
- 不加载桌宠 persona
- 温度 `0.0`，输出限定为 JSON

```json
{"decision":"allow|reject|review","category":"normal|advertising|flooding|scam|other","reason":"..."}
```

### 8.3 为什么“你好”应该通过

- 简短但有交流意义不等于灌水
- 只有结合重复历史才能判断刷屏
- 友链申请中的网址不应天然视为广告
- 模型不可用或结果无法解析时进入人工审核，而非直接拒绝

## 九、同一邮箱的历史上下文

- 每次审核携带同一 `actor_hash` 的历史记录
- 原始邮箱不会发送给模型
- 目标：识别连续灌水、重复广告与上下文相关回复
- 超出字符预算时
  - 保留最近记录
  - 汇总更早记录的状态数量
  - 标记 `truncated`
- [代码片段候选] `_history_payload`

## 十、Prompt Injection 与审核失败策略

- 评论 JSON 包裹在 `<comment_data>` 中
- 系统提示明确把所有字段视为不可信数据
- 严格解析 JSON 决策，不接受自然语言闲聊
- ProviderError / 解析错误统一降级为 `review`
- [补充] 测试过的注入样例与边界案例

## 十一、管理员能力与公开能力分离

- 博客端：密钥进入站长模式、站长标记、删除公开评论
- tonks-home：集中查看两个房间、待审核项与友链申请
- 所有人可读公开评论；只有管理员可见邮箱、审核理由与非公开状态
- 审核与删除接口通过管理员密钥保护
- [补充] 为什么暂时没有在博客里实现完整后台

## 十二、友链申请为何独立于普通评论

- 独立表、独立状态、独立管理入口
- 避免把结构化站点信息塞进评论正文
- 申请页明确展示本站信息、互换原则与复制模板
- AI 评论审核不会把正常友链申请误判为普通广告

## 十三、与 Twikoo、Waline 的对比

| 维度 | 自建系统 | Twikoo / Waline |
| --- | --- | --- |
| 部署与接入 | [补充] | [补充] |
| 数据模型可控性 | 房间、评论树、友链申请可定制 | 通用评论模型更成熟 |
| 管理后台 | 需要自己建设 | 现成功能更完整 |
| 反垃圾与安全维护 | 自己承担 | 社区经验与内建能力更丰富 |
| 邮件通知与社交登录 | 尚未实现 | 通常有成熟集成 |
| 主题一致性 | 可与两个前端深度融合 | 需要覆盖默认组件样式 |
| AI 审核 | 可传入同一邮箱历史并自定义策略 | 取决于插件/二次开发 |
| 运维成本 | 较高 | 相对更低 |

### 13.1 “重复造轮子”是否值得

- 学习目标：数据建模、权限、滥用防护、LLM 结构化输出
- 产品目标：跨 blog 与 tonks-home 的群聊式体验
- 不把自建等同于更安全；安全取决于持续维护
- [补充] 哪些部分值得自研，哪些应借鉴成熟项目

### 13.2 是否需要迁移

- 当前建议：不迁移，先完成现有系统的安全与可观测性基线
- 重新评估迁移的触发条件
  - 评论量显著增长
  - 邮件通知/社交登录成为刚需
  - 垃圾评论对抗成本失控
  - 管理后台维护成本超过个性化收益
- 可保留导出层，避免未来被 SQLite 表结构锁死

- 评论字段与页面白名单校验

## 十五、仍需补齐的生产能力

- 邮箱验证与通知
